# Beta capability handshake activation preflight

## Scope

This preflight is based on `6c20b167bb43063490e8bcac189dd5af8e343a87`
and adds the missing production lifecycle for the existing capability v1
protocol. It changes Server code only. It does not enable a Beta feature,
change repository defaults, change the Client, deploy an artifact, or launch
Paper or Minecraft.

## Missing production path

The existing protocol runtime could encode and send
`projects:beta_caps_v1`, accept `projects:beta_ack_v1`, and gate element state
on a negotiated capability. No production event initiated the advertisement,
so a real Client could not create an acknowledged session. The element state
publisher was therefore correctly gated but unreachable in live operation.

## Live lifecycle

The production publisher now owns this sequence:

1. The protocol module registers its channels.
2. The lifecycle listener is registered.
3. Already-online players are checked on the next server tick.
4. A `PlayerRegisterChannelEvent` for `projects:beta_caps_v1` is the primary
   advertisement trigger.
5. An admitted, listening player receives the existing capability v1 payload.
6. `projects:beta_ack_v1` is decoded and acknowledged by the existing session
   service.
7. State packets remain blocked until that acknowledgement succeeds.
8. Quit, kick, reconnect, module stop, and runtime close remove per-viewer
   session and revision state.

Join does not assume that the Client has registered its plugin channels yet.
It resets stale state and waits for channel registration. The next-tick scan
covers Clients whose channels were already registered when the module starts.

## Admission rules

Advertisement requires all of the following at send time:

- the protocol module is `RUNNING`;
- the protocol runtime is running and not closed;
- `CLIENT_BETA_UI` is enabled;
- the activation audience is `ALLOWLIST` or `GLOBAL`;
- an `ALLOWLIST` audience contains the player UUID;
- the player's current world is allowed;
- the player is listening on `projects:beta_caps_v1`.

`require-compatible-client` is intentionally not an advertisement prerequisite:
compatibility is learned by this handshake. Ineligible players receive no
packet and are not kicked or otherwise mutated.

## Session, duplicate, and ACK behavior

The payload is generated by `ClientBetaProtocolRuntime` and the existing
`BetaProtocolCodec` and session service. The advertised capability set is the
existing configured set; the current production composition advertises only
`ELEMENTS`. Party and mob state are not added by this change.

Before acknowledgement, a duplicate capability-channel registration resends
the exact retained bytes, session ID, and revision. It does not allocate a new
session. After acknowledgement, duplicate registration sends nothing. Expired,
unknown, mismatched, malformed, and superseded acknowledgements are rejected
without disconnecting the player. Reconnect creates a new session, so an ACK
from the previous connection cannot unlock state.

Pending advertisements and protocol sessions are bounded by the existing
capability policy and expire on its TTL. Retained publisher state contains
UUIDs, immutable protocol identifiers, bounded packet bytes, timestamps, and
counters; it does not retain Bukkit `Player` objects.

## Start, failure, and stop behavior

Start order is channel registration, advertisement lifecycle registration, and
then element publisher start. A partial start failure unwinds registered work
in reverse order. Stop continues cleanup after an individual cleanup failure
and is idempotent. Scheduled existing-player checks are cancelled, listeners
are unregistered, pending advertisements are cleared, sessions are closed, and
viewer revision state is removed. A stopped or closed runtime cannot send a
new advertisement.

## Diagnostics

The read-only Beta health response includes bounded aggregate handshake data:
advertisements sent, duplicate resends, accepted and rejected ACKs, active
sessions, and the last bounded result. It does not expose player UUIDs, session
IDs, packet bytes, or a mutation command.

## Staging prerequisites

Repository defaults still produce zero Beta listener registrations, channel
registrations, scheduler tasks, and packets. Before a later staging activation:

- approve a non-`OFF` audience and explicit player/world scope;
- enable `CLIENT_BETA_UI` and only the intended producer capability;
- install a matching Client that registers both capability channels, validates
  the v1 advertisement, and returns the existing v1 ACK;
- confirm through read-only health output that ACK acceptance and active
  sessions match the intended audience;
- exercise reconnect, duplicate registration, malformed/expired ACK, and
  shutdown while observing that non-admitted and legacy Clients are unaffected.

## Verification and rollback

Automated verification is limited to the repository checks and build with
`-PskipAutoStart`. No deployment or game launch is part of this preflight.
Rollback is a revert of this change while repository flags remain false; there
is no data migration or Client rollback requirement.
